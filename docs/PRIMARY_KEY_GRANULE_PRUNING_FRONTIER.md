# Offline UInt64 Primary-Key Granule Pruning Frontier

Document status: implemented and verified for immutable, genuine ClickHouse
26.7-produced adaptive Wide parts in the admitted subset. Content-hash
verification and real-table performance measurement remain outside this slice.

Current frontier: on an immutable offline Atomic table whose engine is exactly
`MergeTree`, select a conservative subset of Wide-part granules for an inclusive
range on one ascending, stored `UInt64` primary key. This is sparse-index
candidate selection, not a SQL `WHERE` result or ClickHouse server snapshot.
The physical part set remains governed by
[`OFFLINE_MERGETREE_PART_RESOLUTION_FRONTIER.md`](OFFLINE_MERGETREE_PART_RESOLUTION_FRONTIER.md).

## Factual anchor and failure to prevent

Before this slice, `OfflineTable#scan_uint64` resolved physical part coverage
and then `WidePartTable#scan_rows` visited every data mark. The DDL parser
retained columns and engine but not key semantics. `WidePart` could read a numbered mark range,
yet marks contain stream offsets, not key values. The inspected ClickHouse
26.6 source uses a sparse per-granule primary index (`primary.idx` or
`primary.cidx`) to choose candidate mark ranges; the test fixture producer is
ClickHouse local 26.7.1.1315, so its generated bytes are the compatibility
evidence for that version. A range scan that mistakes a sparse entry for a
per-row filter can silently omit matching rows, especially at duplicate-key
granule boundaries.

## Admitted surface

- A separate `scan_uint64_pk_candidates` API accepts selected exact `UInt64`
  columns and an inclusive `UInt64` lower and/or upper bound. At least one
  bound is required; an inverted range is rejected. The one recognized key
  column must be selected so caller code can apply the residual row predicate.
- Only a simple ascending stored `UInt64` `ORDER BY` key with no divergent or
  unsupported explicit `PRIMARY KEY` expression is admitted. Unsupported DDL
  remains usable by existing full scans but rejects this new API.
- Resolve the same safe physical part set as existing scans. Before any data
  callback, validate the supported sparse-index file and entry count for every
  selected part, including selected checksum size, bounded decode, monotonic
  keys, and its relationship to the part's data marks. Treat `primary.idx`
  and `primary.cidx` as distinct encodings; never reinterpret compressed bytes
  as raw keys. A missing, ambiguous, malformed, or unsupported index rejects.
- Select a conservative mark interval per part. Include the predecessor mark
  where a lower bound may fall inside a granule, and retain every duplicate-key
  boundary mark that may contain a matching row. Skipped marks are not decoded.
- Yield *whole candidate-granule batches*, preserving original part, mark,
  part-row, and source-row offsets, including gaps from pruned granules. The
  callback must still compare each row's key to the requested bounds; a
  candidate batch is not an exact match set. Existing `scan_*` behavior stays
  unchanged.

## Rejected and guard-only surface

- No SQL/parser, composite or expression keys, descending order, nullable or
  non-`UInt64` keys, alternate key ordering, skip indexes, partition/min-max
  pruning, Compact parts, projections, TTL-suffixed DDL, or server
  Active/snapshot inference.
- No fail-open full scan on a malformed/unsupported index in this API. The
  caller may explicitly choose the existing full-scan API instead.
- No exact row filtering by the reader in this slice. That would require a
  distinct callback contract for narrowed rows and provenance; residual
  filtering belongs in Crystal caller code.
- Index-to-payload agreement and filesystem immutability are assumed within
  the existing offline part contract; size checks are not hash verification.
  In particular, changing a raw sparse key from `[0, 0, 1, 2, 3, 4]` to
  `[0, 1, 1, 2, 3, 4]` preserves length and monotonicity but can make an
  equality probe for zero skip a genuine matching granule. The caller must
  trust immutable ClickHouse-produced parts until index hashes and frame
  checksums are verified; this API is not a corruption-proof reader.

## Intended Crystal call

```crystal
table = CrystalClick::OfflineCatalog.open("/var/lib/clickhouse").table("lab", "events")
table.scan_uint64_pk_candidates(["pk", "value"], lower_bound: 10_u64, upper_bound: 20_u64) do |batch|
  keys = batch.values_for("pk")
  values = batch.values_for("value")
  keys.each_with_index do |key, row|
    next unless key >= 10_u64 && key <= 20_u64
    process_row(key, values[row])
  end
end
```

The callback is once per candidate mark, not bounded by the full-scan
`batch_rows` parameter. The inherited mark cap is 65,536 rows; the caller
must not retain slices beyond the callback. This API inherits the reader's
adaptive Wide-part `.mrk2`/`.cmrk2` support and does not handle legacy
fixed-granularity `.mrk` parts.

## Design laws and falsifiers

Risk: CAUTION. The strongest failure is a false negative caused by selecting
too few granules. The cheapest discriminator is comparison against an
independently filtered full scan of the same public ClickHouse-produced part.

1. Generate a public multi-granule part with a simple `UInt64` key and keys
   duplicated across granule boundaries. Exercise supported raw and compressed
   primary-index encodings. Check source key/value pairs independently.
2. For equality, bounded range, lower-only, upper-only, no-match, and all-match
   cases, client-filtered candidate batches must equal client-filtered full
   scan rows and provenance. A selective case must visit fewer mark ordinals
   than the full scan.
3. Unsupported DDL, absent index, wrong index length, unsorted keys, malformed
   compressed frame, symlink, and checksum-size mismatch must fail before the
   first callback. An unrelated covered part's index need not be opened, but
   existing transaction and delete-mask guards still apply.
4. Skipped marks must still count toward physical part/source offsets;
   callback exceptions propagate unchanged. Existing full-scan tests must
   remain green.

DoD: focused PK specs red before implementation and green after; fixture shape
check; full debug and release specs; `crystal tool format --check src spec` and
`git diff --check`; source-bound adversarial review of boundary marks, DDL
recognition, and no-callback failures. Rollback is the scoped feature commit.
Evidence decays when ClickHouse primary-index serialization, DDL output,
Wide-part mark semantics, or the offline scan callback contract changes.

Implementation seal: `scan_uint64_pk_candidates` preflights all selected
parts' indexes before a callback, handles raw and framed compressed indexes,
and emits whole candidate marks with physical offsets. The public fixture
generator pins ClickHouse local 26.7.1.1315; `--check` established five
eight-row data marks plus a final sentinel for each of two 40-row parts.
The focused red test initially failed on the absent API, then the expanded
focused suite passed 10/10. Full debug and release suites each passed 222/222
with Apple ld (`--link-flags='-fuse-ld=ld'`); format, fixture, shell syntax,
and diff checks passed. The adversarial verdict is ROBUST only under the
stated faithful-index and immutable-part assumptions. A same-size index
mutation that passes structural checks is the explicit falsifier for any
broader integrity claim. No wall-clock speedup is claimed from these tests.
